# Item Loading and Static Cache Rules

This document defines the architecture, design guidelines, and API contracts for item loading, caching, and database sweep operations within BetterBags.

## Architectural Guidelines

### 1. Static ItemMixin Caching (Zero-Allocation Design)
Historically, the data sweep phase dynamically instantiated transient `ItemMixin` objects on every `BAG_UPDATE` or full scan. This placed significant pressure on the Lua garbage collector and introduced potential framerate micro-stutters.
- **Rule:** Every physical bag slot (`bagID` and `slotID`) must map to a single, permanently cached `ItemMixin` instance.
- **Registry:** `ItemLoader` maintains this permanent cache in `self.itemMixinsBySlotKey` indexed by `slotKey` (formatted as `"bagID_slotID"`).
- **Access:** Other subsystems (like `data/items.lua`) must retrieve `ItemMixin` instances from the cache via:
  ```lua
  local itemLoader = addon:GetModule('ItemLoader')
  local itemMixin = itemLoader:GetItemMixinFromSlotKey(slotKey)
  ```
- **Mutation:** The cached `ItemMixin` handles any item changes internally when queried (as its state is bound by slot location, not static values). Therefore, the cached mixin should never be recreated or released back to any pool.

### 2. Native Asynchronous Cache-Priming via `ContinuableContainer`
To prevent visual flickers, blank slots, and lag-induced loading glitches, UI rendering must only occur after the client's internal C-level cache is fully primed with item data.
- **Rule:** Never attempt to read details or draw items from a raw, uncached `BAG_UPDATE` event.
- **Mechanism:** Utilize Blizzard's native `ContinuableContainer` inside `ItemLoader` to batch and pre-load all changed item mixins.
- **Callback:** The `ItemLoader:TellMeWhenABagIsUpdated(callback)` registry acts as the gatekeeper. The callback fires only after the `ContinuableContainer` completes loading all queued mixins.

### 3. Unified Update Flow (Stateless, Zero-Debounce Execution)
- `BAG_UPDATE` is registered and buckets updated bag IDs.
- `BAG_UPDATE_DELAYED` triggers `ProcessPendingBagUpdates()`.
- Pending bag slots are scanned, and their static mixins are queued into `ContinuableContainer`.
- `ContinueOnLoad` executes the callbacks.
- The `Refresh` module receives the callback and immediately requests draws/refreshes instantly and synchronously with a completely primed cache.
- **Single Frame Boundary:** `items:ProcessRefresh` runs inside an `async:Do` coroutine and yields exactly once, immediately after `Phase2_Harvest`. The harvest reads the client in the frame the event fired; every later phase (previous-state extraction, targeted merge, enrichment, sorting, partition, commit and draw) resumes via `C_Timer.After(0)` on the next frame. Because refreshes resume in the order they were queued, a refresh started in the same frame as another always merges against the state the earlier one just committed. Never place the yield after `Phase3_ExtractPreviousState`: with the yield before the commit, a same-frame wipe + targeted sweep pair ended with the targeted sweep committing only its own bags (see `spec/refresh_pipeline_spec.lua`).
- **Rule:** The `Refresh` module is completely stateless. It does not maintain arbitrary timer debounces (`C_Timer.NewTimer`), pending wipe flags, or stateful flags like `pendingBackpack` or `pendingBank`. Redraw requests trigger synchronously at the natural `BAG_UPDATE_DELAYED` frame boundary. Data sweeps can execute perfectly at any time, including during combat, as data-harvesting is fully decoupled from secure layout frames.
- **Combat Gating:** All item updates and bag redraws execute completely un-gated and synchronously during active combat, because physical item buttons are pre-allocated and statically bound to `bagID` and `slotID` at startup. Updating textures, counts, item levels, and layout anchoring on insecure frames in combat does not trigger Blizzard "Action blocked" taint errors. Bag sorting (`request.sort`) remains the only action explicitly guarded behind `not InCombatLockdown()` because `C_Container.SortBags` uses protected Blizzard container APIs.
- **Initial Startup Refresh:** To prevent bags from appearing completely blank on initial login or UI reload, `Refresh:OnEnable()` must explicitly trigger an initial full-cache wipe update (`wipe = true, backpack = true, bank = true`) once all modules are active.
- **Core Invalidation Events:** Standard events (`BAG_CONTAINER_UPDATE`, `EQUIPMENT_SETS_CHANGED`) and Classic-specific events (`PLAYERBANKSLOTS_CHANGED`) must be registered to trigger target cache-wipe redraws, ensuring perfect visual synchronization across all retail and classic environments.

### 4. Unified Retail Bank Loading and Persistent Tab Filtering
To support instant, synchronous tab switching with zero visual flickers or loading stutters:
- **Unified Cache:** On Retail, the data-loading pipeline (`data/items.lua`) always loads all bank bags (both Character Bank and Account/Warbank bags) into a single, unified `slotInfo` cache, regardless of the active tab.
- **Strict Filtering:** Upstream pipeline (`data/items.lua`) in Phase 4.5 strictly partitions this complete cache into `slotInfo.tabs` and filters out hidden categories and irrelevant bank type items. Items in `ACCOUNT_BANK_BAGS` only populate Account/Warbank tabs, while items in `BANK_BAGS` only populate Character Bank tabs.
- **Bypass for Blizzard Bag View:** If the active view mode is Blizzard's physical container view (`SECTION_ALL_BAGS`), the partition filtering and section group-hiding filters are completely bypassed. This ensures that when a user switches to Blizzard Bag View, all physical bag containers and their items render completely and synchronously, regardless of the active custom tab/group.
- **Instant Swapping:** Since the cache is always complete, tab switching (`SwitchToGroup` or `SwitchToBlizzardTab`) does not wipe caches or trigger server-refresh messages. Instead, the UI simply hides the old view, fetches the new view, and calls `Draw()` synchronously and instantly.

### 6. Idempotent Functional Rendering (No Changeset Gating)
To enforce strict functional isolation and eliminate UI state leakage or out-of-order rendering bugs, changeset-gating and background rendering optimizations have been completely removed.
- **Rule:** Every rendering pass for any view (whether active or background) must be 100% functional, idempotent, and built completely from scratch using the provided `slotInfo` dataset state.
- **Benefits:** Eliminating incremental delta updates guarantees that the view state remains mathematically consistent with the underlying data model, preventing the visual accumulation of ghost or out-of-sync frames.

### 7. Phase 8: Page Placement (Clean-Sweep Layout and Column-Packing)
To achieve sub-millisecond redraw performance while ensuring that the grid layout remains perfectly aligned, visually fluid, and free of overlap/gaps:
- **Rule:** Page placement is a pure, top-down clean-sweep operation. It is triggered synchronously when the data backend emits `items/RefreshBackpack/Done` or `items/RefreshBank/Done` messages.
- **Unified Views:** GridView, OneBagView, and Blizzard Bag View are handled polymorphically within `views/gridview.lua` and `views/bagview.lua`. They avoid redundant layout files by treating views as alternative naming classifications.
- **Two-Pass Column packing:**
  - **Pass 1:** Determines the default height/width of all category sections and splits them into equal-height vertical columns using the `calculateColumns` algorithm inside `frames/grid.lua`.
  - **Pass 2 (Row collapse shrink optimization):** Measures row-level layouts to shrink-wrap category sections when all items within a row are collapsed. This dynamically adjusts bounding heights and prevents massive blank gaps.
- **Bounds Clamping:** The view calculates the total bag height and width, clamps the parent frame within safe screen limits (`UIParent:GetHeight() * 0.90`), and toggles the scrollbars and frame points dynamically.
- **Shared, Stateless Sizing (`UpdateBagBounds`):** To ensure uniform sizing when switching tabs instantly without caching state, all bag views call a shared, stateless helper method `view:UpdateBagBounds(bag, w, h)`. This centralizes the bounds calculations, clamping, scrollbar visibility, and search-offset positioning. It is invoked at the end of the full rendering pipeline, achieving visual size parity with zero state-holding overhead.

### 8. Phase 4.5: Category Enrichment & Data Enrichment
To eliminate JIT (just-in-time) database and search engine queries during UI layout rendering, we assign final item categories and enrich item data right after search indexing and before layout/section placement occurs.
- **Rule:** Item categories must never be resolved JIT on-the-fly inside the views (`GridView` or `BagView`). Instead, they are retrieved instantly from the enriched `item.itemInfo.category` field.
- **Mechanism:** Immediately after Phase 4's search indexing `search:IndexItems(itemData)` completes (`items:Phase8_EnrichCategories(ctx, kind, itemData, emptySlotByBagAndSlot)`):
  - Call `self:RefreshSearchCache(kind, itemData)` to update search-based category matches using the search engine.
  - Iterate over all non-empty items in `itemData` and resolve their final category by calling `items:GetCategory(ctx, item)` again. `GetCategory` is the single place where Recent Items, gear sets, custom item-list categories and search categories compete by priority (lower number wins, search wins ties). Phase 6 also calls `GetCategory`, but it does so against the *previous* sweep's search cache; the Phase 8 pass is what makes the result correct for this sweep. Never overwrite `item.itemInfo.category` with the raw search-cache entry: that bypasses the priority rules and lets a priority-10 search category beat a priority-1 custom category.
  - When the category changed, update `item.itemInfo.category` and refresh the search index's category with `search:UpdateCategoryIndex(currentItem, oldCategory)`.
  - **Live Search Results:** The active search box text is external input, in the same class as a `C_Container` read: it is consumed by the data phase and never by the draw phase. It is evaluated here (`data.isSearchResult`), never in Phase 6 and never in a view. Phase 6 runs before `search:IndexItems`, so evaluating there queries the previous sweep's index and newly looted or moved items never match until the following refresh. Views only read the pre-computed `data.isSearchResult` flag; they must not call `SearchBox:GetText()` or `search:Search()` themselves.
- **Upstream Category Visibility Filtering:** During the partition of items and categories into `slotInfo.tabs`, we query `categories:IsCategoryShown(category)`. If a category is hidden by the user, its items and its category metadata are completely omitted from `tabData.items` and `tabData.categories` upstream, so the view only ever receives and draws active, visible sections. This completely eliminates late-stage masking and filtering in the views.
- **Pure Data-Driven physical layout (Show Bags / `SECTION_ALL_BAGS`):** When the database layout view is set to `SECTION_ALL_BAGS`, the data phase overrides all physical item categories to their physical bag names (e.g. `#1: Backpack` or `#1: Bank`). It attaches rendering instructions to the slot data structure (`slotInfo.sectionLayouts`) indicating that these sections must be drawn headerless (`hideHeader = true`) and sorted strictly by physical slot (`sortMode = "physical"`). The view layer (`views/bagview.lua` and `views/gridview.lua`) remains completely dumb; it parses the categories and obeys `slotInfo.sectionLayouts` metadata without any hardcoded layout checks.
- **Synchronous, State-Driven Toggle:** The "Show Bags" buttons synchronously mutate the database view state and trigger immediate refresh events (`FullRefreshAll`). All asynchronous OnFinished animation hooks that previously modified state or initiated refreshes have been completely removed.
- **Obsolete Views:** Obsolete `ONE_BAG` (value 1) and `LIST` (value 3) views have been completely removed from constants and database defaults. Existing users' databases are automatically migrated to `SECTION_GRID` (Category View) via `DB:Migrate()`.

### 9. Isolated Wipe-On-Render to Prevent Pool Contamination and Anchor Crashes
To permanently prevent ObjectPool contamination, cell leakage, and fatal `Cannot anchor to itself` crashes during layout recalculations:
- **Rule:** Every rendering pass for a view is functionally isolated and begins with a complete, synchronous wipe of its own frames, returning all of its pooled elements back to the global stacks before any rendering/population occurs.
- **Mechanism:** The very first line of each view's `Render` method (e.g. `GridView` or `BagView`) executes `view:Wipe(ctx)`.
- **State Transition (`isNew` flag):** Inside `Wipe(view, ctx)`, explicitly set `view.isNew = true` to flag the view as completely empty. At the beginning of the `Render` method (right after wiping), set `view.isNew = false` to indicate the view is populated and complete. This guarantees 100% clean-slate rendering on every single frame update.

### 10. Unidirectional, Purely Functional Pipeline and Stateless Execution
To enforce strict functional isolation and eliminate side-effects, reentrancy bugs, and half-calculated visual glitches during database updates:
- **Rule:** The entire rendering and data-refresh pipeline (`ProcessRefresh`) is structured as a purely unidirectional, functional pipeline of discrete phase functions. It avoids mutating any global or committed state (such as `self.slotInfo[kind]`) until the final phase (`Phase8_CommitAndDispatch`).
- **Transient State Isolation:** We completely avoid global/module-level JIT queries or the `_tempSlotInfo` hack.
  - An un-registered `emptySlotData` object (instantiated locally via `self:NewSlotInfo()`) acts as a transient container for empty slots, free keys, and item counts.
  - Explicit maps and dictionaries (such as `itemData` and `visibleItemsBySlotKey`) are passed linearly as arguments between the phase functions (e.g. `items:RefreshSearchCache(kind, itemData)` and `stack:AddToStack(item, itemData)`). This ensures statelessness and permanently prevents stale-state reads during calculation.
- **Commit Phase:** At the end of the pipeline, `Phase8_CommitAndDispatch` copies all calculated tables, totals, layout metadata, and the newly calculated `stackData` atomically and transactionally from the transient data structures to the real, stateful `self.slotInfo[kind]`, ensuring atomic updates and zero half-finished visual states.

### 11. Targeted Data Sweeps and Targeted State Merging
To minimize CPU frame time and `C_Container` API scanning overhead during localized item changes (such as looting an item, casting a spell, or moving an item in a single bag slot):
- **Rule:** `BAG_UPDATE` events trigger targeted bag harvesting. `Phase1_DetermineBags` intercepts `ctx:Get("targetedBags")`. When present (and not performing a forced cache `wipe`), `Phase1_DetermineBags` filters the active bag list to harvest only the specific `bagID`s that changed.
- **Nil Means All:** Global operations (sorting bags, switching tabs, category updates, initial login/UI reload, or explicit `bags/FullRefreshAll` messages) omit the `bags` field in `RefreshRequest`. When `targetedBags` is `nil` or `ctx:Get("wipe")` is `true`, `Phase1_DetermineBags` automatically falls back to sweeping all available container bags.
- **Targeted Merging:** In `ProcessRefresh`, when a targeted sweep completes, newly harvested `itemData` for the targeted bags is merged with `previousItems`: slot keys belonging to targeted bags are cleared from `previousItems`, and newly harvested slots are inserted. The resulting complete, unified `itemData` dictionary is then passed down to downstream phases (virtual stacking, search indexing, category enrichment, sorting, tab partitioning), ensuring downstream phases always operate on a 100% complete model of all bags. `previousItems` is read *after* the frame boundary (§3), so it always reflects the most recent commit, including commits from refreshes that were queued earlier in the same frame.
- **Moved Items (`Phase4_ClearMovedItemGlows`):** An item whose GUID disappears from one slot and appears in another in the same sweep was moved, not looted. Its new-item state is cleared through `items:ClearNewItemFromData(ctx, addedItem)` on the harvested data object. Phase functions must never reach for committed state (`GetItemDataFromSlotKey`) to mutate an item they were handed: the committed entry for the destination slot is the previous occupant of that slot (or nothing), so the moved item's GUID timer would never be cleared and it would stay in Recent Items.
- **Classic Base Bank Support:** On Classic/Era clients, `PLAYERBANKSLOTS_CHANGED` passes `bags = { [-1] = true }` to target the base bank slot changes specifically, preventing unnecessary full bank cache wipes.

### 12. Scoped Recent Item Tracking and Sort Pipeline Integration
To prevent global side-effects where sorting or clearing recent items in one container (e.g. Backpack) accidentally clears recent item timers in another container (e.g. Bank/Warbank):
- **Scoped Timers:** `_newItemTimers` inside `data/items.lua` is strictly scoped by `BAG_KIND` (`BACKPACK` vs `BANK`).
- **Targeted Clearing:** `items:ClearNewItems(kind)` accepts a `BAG_KIND`. Passing `BACKPACK` clears only `BACKPACK` timers and invocations of `C_NewItems.RemoveNewItem` for backpack bag IDs. Passing `BANK` clears only `BANK` timers and `C_NewItems` for bank and account bank bag IDs.
- **Sort Integration:** Sorting requests (`request.sort`, `request.sortBank`, `request.sortWarbank` in `data/refresh.lua`) automatically trigger targeted `items:ClearNewItems(kind)` and force an immediate redraw of the affected bag container (`request.backpack = true` or `request.bank = true`) before invoking the Blizzard C-level sorting APIs (`C_Container.SortBags`, `SortBankBags`, or `SortAccountBankBags`). This ensures Recent Items are cleared and layout categories are re-enriched synchronously in the UI.

### 13. Persistent Empty Gaps (Diff-Driven, No Held State)
To reproduce the classic "the bag doesn't collapse while it's open" behavior, when a displayed item icon leaves a slot (consumed, sold, destroyed, or moved out — including the last physical stack of a virtual stack) we leave a **true empty gap** at that item's exact position in its category section. The gap is a real hole in the grid (no item frame at all), it persists across refreshes, it persists even when new items are added elsewhere, and it collapses only on **Sort**, **bag close**, **bank open**, or a full **wipe**.
- **It is a data-structure problem, not a rendering problem.** The renderer already accepts `isItemGap` nodes (views turn them into frameless `{ isGap = true, width = 37, height = 37 }` cells that `frames/grid.lua` lays out as reserved holes). No view or grid math changed. The only render-side fix was making `sectionProto:ReleaseAllCells` (`frames/section.lua`) skip gap cells, which have no `Release` method.
- **No bespoke held state.** The pipeline stays a stateless clean-sweep (§6, §10). The "previous view" is simply the already-committed `self.slotInfo[kind].sortedItems` (now surfaced by `Phase3_ExtractPreviousState` as a third return, `previousSortedItems`); the "new view" is this sweep's `visibleItemsBySlotKey`. Gaps ride forward inside the committed `sortedItems`, so they persist with zero extra structures to hold or clear.
- **The diff (`items:BuildOrderedItems`, replaces the direct `Phase9_Sort` call in `ProcessRefresh`):** matches previous layout entries against current displayed items **bucketed by `itemHash`** (not GUID — a virtual-stack re-root changes the root's GUID but not its hash). Per hash: (1) a previous slotkey still displayed **survives in place**; (2) leftover current items of that hash fill leftover previous slots of that hash (a move or re-root **rekeys in place, no gap**); (3) any previous entry with no current match becomes a **gap** (a `CloneAsGap` of the departed entry — a shallow copy carrying `bagid`/`itemInfo.category`/`itemHash` so `ItemBelongsToTab` routes the hole to the same tab, `isItemGap = true`, and slotkey `"gap:"..originalSlotkey` which never collides with a real `"bagid_slotid"`); (4) genuinely new displayed items are **appended** at the end of their category in fresh attribute-sort order (they never backfill a gap). Gaps are excluded from `totalItems` (Phase 10) and keep their category alive in the category tally.
- **Reset (fresh, gapless attribute sort) vs. diff:** `BuildOrderedItems` returns a plain `Phase9_Sort` (no gaps) when the physical bag view (`SECTION_ALL_BAGS`, which already renders empties in place and never collapses), when the option is off, when `ctx:Get("resetLayout")` is set, when the bag is closed (`items:IsBagOpen(kind)` is false), or when there is no previous layout (first load / post-wipe). That gapless result becomes the next baseline.
- **Lifecycle triggers.** `resetLayout` is set in `data/refresh.lua` on every Sort branch (`request.sort`/`sortBank`/`sortWarbank`) and on `BANKFRAME_OPENED` (opening the bank starts clean). Full wipes (`bags/FullRefreshAll`, `BAG_CONTAINER_UPDATE`, etc.) reset the slotInfo, so `previousSortedItems` is empty and the sweep is gapless. Bag close reuses the dormant `drawOnClose` flag: `BuildOrderedItems` calls `items:MarkDrawOnClose(kind)` whenever it emits a gap, and the backpack `OnHide` path (`bags/backpack.lua`) already re-refreshes when `drawOnClose` is set — the frame is hidden by then, so the on-close sweep sees `IsBagOpen == false` and commits a collapsed layout. Consuming items while the bag is closed likewise never accrues gaps.
- **Per-kind scoping.** State lives entirely in each kind's committed `slotInfo[kind].sortedItems`, so backpack and bank/warbank gaps are structurally isolated; a bank consume can never gap the backpack.
- **Option.** `database:GetPreserveItemGaps(kind)` / `SetPreserveItemGaps(kind, value)` (default **on** per kind via `const.DATABASE_DEFAULTS`), exposed as the "Preserve Empty Slots as Gaps" checkbox in `config/config.lua`; toggling it sends `bags/FullRefreshAll` for a clean transition.
