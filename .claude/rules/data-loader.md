# Item Loading and Static Cache Rules

This document defines the architecture, design guidelines, and API contracts for item loading, caching, and database sweep operations within BetterBags.

## Architectural Guidelines

### 1. Static ItemMixin Caching (Zero-Allocation Design)
Historically, the data sweep phase dynamically instantiated transient `ItemMixin` objects on every `BAG_UPDATE` or full scan. This placed significant pressure on the Lua garbage collector and introduced potential framerate micro-stutters.
- **Rule:** Every physical bag slot (`bagID` and `slotID`) must map to a single, permanently cached `ItemMixin` instance.
- **Registry:** `ItemLoader` maintains this permanent cache in `self.itemMixinsBySlotKey` indexed by `slotKey` (formatted as `"bagID_slotID"`).
- **Access:** Other subsystems (like `data/items.lua`) must retrieve `ItemMixin` instances from the cache via:
  ```lua
  local itemLoader = addon:GetModule('ItemLoader')
  local itemMixin = itemLoader:GetItemMixinFromSlotKey(slotKey)
  ```
- **Mutation:** The cached `ItemMixin` handles any item changes internally when queried (as its state is bound by slot location, not static values). Therefore, the cached mixin should never be recreated or released back to any pool.

### 2. Native Asynchronous Cache-Priming via `ContinuableContainer`
To prevent visual flickers, blank slots, and lag-induced loading glitches, UI rendering must only occur after the client's internal C-level cache is fully primed with item data.
- **Rule:** Never attempt to read details or draw items from a raw, uncached `BAG_UPDATE` event.
- **Mechanism:** Utilize Blizzard's native `ContinuableContainer` inside `ItemLoader` to batch and pre-load all changed item mixins.
- **Callback:** The `ItemLoader:TellMeWhenABagIsUpdated(callback)` registry acts as the gatekeeper. The callback fires only after the `ContinuableContainer` completes loading all queued mixins.

### 3. Unified Update Flow (Stateless, Zero-Debounce Execution)
- `BAG_UPDATE` is registered and buckets updated bag IDs.
- `BAG_UPDATE_DELAYED` triggers `ProcessPendingBagUpdates()`.
- Pending bag slots are scanned, and their static mixins are queued into `ContinuableContainer`.
- `ContinueOnLoad` executes the callbacks.
- The `Refresh` module receives the callback and immediately requests draws/refreshes instantly and synchronously with a completely primed cache.
- **Single Frame Boundary & Serialized Queue:** the data sweep for one bag kind lives in `items:RunRefresh(ectx, kind)`, which yields exactly once, immediately after `Phase2_Harvest`. The harvest reads the client in the frame it runs; every later phase (previous-state extraction, targeted merge, enrichment, sorting, partition, commit and draw) resumes on a later frame. **All refreshes are serialized through the single frame-stepped queue in `data/refresh.lua` (see refresh-scheduler.md):** `RequestUpdate` only enqueues, and the pump runs exactly one request-unit at a time — never two sweeps in flight — so a unit's `Phase3_ExtractPreviousState` always reads the fully-committed state of the strictly-previous unit, and no request-time mutation (`ClearItemCache`/`ClearNewItems`/Sort) of an earlier-queued wipe can empty the cache underneath a parked sweep. `items:RunRefresh` is still driveable directly via the `items:ProcessRefresh` (`async:Do`) wrapper for unit tests, but production always goes through the scheduler. Keep the yield after `Phase2_Harvest` and before `Phase3_ExtractPreviousState`: it splits the heavy harvest off the commit frame (script-timeout protection) — the cross-refresh ordering it once guarded is now guaranteed structurally by the queue.
- **Rule:** The `Refresh` module is completely stateless. It does not maintain arbitrary timer debounces (`C_Timer.NewTimer`), pending wipe flags, or stateful flags like `pendingBackpack` or `pendingBank`. Redraw requests trigger synchronously at the natural `BAG_UPDATE_DELAYED` frame boundary. **One narrow exception:** a sort arms a one-shot fallback timer (`refresh:_ArmSortFallback`), and the "sort sweep pending" mark it checks lives in Items (`items._sortSweepPending`, like `_firstLoad`). It is not a debounce: it never delays or drops a refresh, it can only add one, and only for a sort whose result no sweep has shown yet (refresh-scheduler.md §6). **One more:** from `OnEnable` until the startup read, the queue is held (`refresh._held`, `refresh._startup`) so that the first read of the bags happens once the client has delivered them (refresh-scheduler.md §8). It holds requests, never drops them, and ends for good at the first read. Data sweeps can execute perfectly at any time, including during combat, as data-harvesting is fully decoupled from secure layout frames.
- **Combat Gating:** All item updates and bag redraws execute completely un-gated and synchronously during active combat, because physical item buttons are pre-allocated and statically bound to `bagID` and `slotID` at startup. Updating textures, counts, item levels, and layout anchoring on insecure frames in combat does not trigger Blizzard "Action blocked" taint errors. Bag sorting (`request.sort`) remains the only action explicitly guarded behind `not InCombatLockdown()` because `C_Container.SortBags` uses protected Blizzard container APIs.
- **Initial Startup Read (one read, after the client delivered the bags):** `Refresh:OnEnable()` reads nothing. At PLAYER_LOGIN the client has not delivered the bags yet: a captured cold login showed the old login sweep inside `OnEnable` reading a backpack of 20 empty slots, with the bags and their contents arriving over the next five seconds and 25 refresh units following. `refresh:HoldForStartup()` holds every refresh and the loader until the loading screen has ended, a frame has passed with no bag events, and `itemLoader:PrimeAll` has loaded the item data of every bag slot and every equipped slot; then one wipe of both kinds runs and absorbs everything requested meanwhile (refresh-scheduler.md §8). The first harvest therefore reads the delivered bags with warm item data, and `RunRefresh`'s `_firstLoad` wipe is already satisfied by it. Coverage: `spec/refresh_pipeline_spec.lua` ("the startup read", including a replay of the captured login), `spec/loader_spec.lua` (`Hold`/`Release`/`PrimeAll`), `spec/refresh_spec.lua` ("reads nothing in OnEnable").
  - **Failure mode (issue #1090 — "most items in Everything on login"):** the old `Refresh:OnEnable()` fired `RequestUpdate({ wipe = true, backpack = true, bank = true })` directly, harvesting **synchronously in the same frame** against a possibly-cold cache. `AttachItemInfo` reads `C_Item.GetItemInfo(itemID)`, which returns nil for uncached items, so `itemType`/`itemSubType` fell back to `""` and `GetCategory` dropped the item into `L:G("Everything")` (data/items.lua). It self-heals only if a later `BAG_UPDATE`-driven refresh lands after the cache warms; when those events fired during the loading screen before the loader registered (or nothing else dirtied the bags), the cold result stuck until a `/reload` (which always works because the item cache is warm from the session). Routing the login sweep through the loader's `ContinuableContainer` (`LoadAllBagsAndUpdate`, since replaced by the startup read's `PrimeAll`) removed that race by honoring the same load guarantee every other refresh uses.
  - **Priming alone is not sufficient — categorization must be cold-proof (issue #1090, second fix):** this still holds with the startup read, which reads without the item data when priming times out, and every later wipe harvests without priming. Historically, routing the login sweep through `LoadAllBagsAndUpdate` did **not** eliminate the "Everything on very full bags" symptom, because the `ContinuableContainer` only guarantees the sweep *it* triggers; it does not gate the other refresh units that can commit first and win the `_firstLoad` forced wipe. Two such units harvest a cold cache with no priming at all: the `BAG_CONTAINER_UPDATE` and `EQUIPMENT_SETS_CHANGED` handlers (`data/refresh.lua`), both `RequestUpdate({ wipe = true, backpack = true, bank = true })`, and `EQUIPMENT_SETS_CHANGED` fires during login for any character with equipment sets. Additionally, a real `BAG_UPDATE` unit can be enqueued before the all-bags login container finishes priming (fuller bags → slower to prime → easier to lose the race); `_firstLoad` then upgrades that partially-primed unit to a full-bag wipe (`Phase1_DetermineBags` ignores `targetedBags` under wipe), harvesting the still-cold bags. Any of these commits `itemType`/`itemSubType == ""` → `L:G("Everything")`.
    - **The robust fix:** `AttachItemInfo` sources the five categorization-relevant fields — `itemType`, `itemSubType`, `itemEquipLoc`, `classID`, `subclassID` — from **`C_Item.GetItemInfoInstant(itemID)`**, which never issues a server query and **always returns for a valid item** (verified against `.libraries/wow-ui-source` `Item.lua:GetItemID`/`ValidateForContinueOnItemLoad`, which structurally depend on it resolving before any load, and `ItemDocumentation.lua`). `GetItemInfo` still supplies name/level/sellPrice/bindType/expacID (no instant equivalent; expac heals on the next warm sweep). This makes `GetCategory`'s primary Type/Subtype/EquipmentLocation/TradeSkill routing correct regardless of cache warmth or which refresh unit runs first — Blizzard's own `Blizzard_ContainerFrame` likewise never renders slots from `GetItemInfo`. Each `X = instX or X` line keeps warm-cache and test behavior byte-identical (instant is preferred, `GetItemInfo`/coerced default is the fallback). Coverage: `spec/items_spec.lua` ("Cold item cache categorization (login, issue #1090)": `GetItemInfo` returns nil, `GetItemInfoInstant` supplies the type, item categorizes to its real type instead of "Everything").
- **The bank open read is primed too.** Bank containers have no slots until the bank opens, so `PrimeAll` cannot cover them; `BANKFRAME_OPENED` shows the window, primes the bank (`loader:PrimeBank`) and reads it once loaded, with a timeout (refresh-scheduler.md §11). It used to read at once: captures showed 478 of 491 bank items read cold.
- **Core Invalidation Events:** Standard events (`BAG_CONTAINER_UPDATE`, a wipe; `EQUIPMENT_SETS_CHANGED`, a recalculation of both bags, refresh-scheduler.md §10) and Classic-specific events (`PLAYERBANKSLOTS_CHANGED`) must be registered to trigger refreshes, ensuring perfect visual synchronization across all retail and classic environments. On WoW: Forever `PLAYERBANKSLOTS_CHANGED` means a bank tab's bag socket changed, so it requests a full bank sweep (`{ bank = true }`), never the Classic `bags = { [-1] = true }` target (bag -1 is the keyring there; see camelot-forever.md §9).

### 4. Unified Retail Bank Loading and Persistent Tab Filtering
To support instant, synchronous tab switching with zero visual flickers or loading stutters:
- **Unified Cache:** On Retail, the data-loading pipeline (`data/items.lua`) always loads all bank bags (both Character Bank and Account/Warbank bags) into a single, unified `slotInfo` cache, regardless of the active tab.
- **Strict Filtering:** Upstream pipeline (`data/items.lua`) in Phase 4.5 strictly partitions this complete cache into `slotInfo.tabs` and filters out hidden categories and irrelevant bank type items. Items in `ACCOUNT_BANK_BAGS` only populate Account/Warbank tabs, while items in `BANK_BAGS` only populate Character Bank tabs.
- **Bank-Type Scoped Category Routing:** On Retail, `categoryToGroup[const.BAG_KIND.BANK]` is partitioned by `bankType` (`Enum.BankType.Character` vs `Enum.BankType.Account`). Assigning a category to a Warbank tab does not overwrite or evict the category in the Character Bank, and vice versa. During `ItemBelongsToTab`, if an item's category is unassigned for that item's `bankType`, it safely falls back to the default tab of that bank type (`Tab 1` for Character Bank, `Tab 2` for Warbank). No physical item is ever dropped into zero tabs.
- **Non-Retail Isolation:** Non-retail clients (`not addon.isRetail`) have no Warbank and no `Enum.BankType`. They maintain the single flat `categoryToGroup[BANK]` namespace without bankType scoping.
- **Bypass for Blizzard Bag View:** If the active view mode is Blizzard's physical container view (`SECTION_ALL_BAGS`), the partition filtering and section group-hiding filters are completely bypassed. This ensures that when a user switches to Blizzard Bag View, all physical bag containers and their items render completely and synchronously, regardless of the active custom tab/group.
- **Instant Swapping:** Since the cache is always complete, tab switching (`SwitchToGroup` or `SwitchToBlizzardTab`) does not wipe caches or trigger server-refresh messages. Instead, the UI simply hides the old view, fetches the new view, and calls `Draw()` synchronously and instantly. Only the active tab's view is rendered by a draw; the others are drawn when switched to (layout-rendering.md §1).

### 6. Idempotent Functional Rendering (No Changeset Gating)
To enforce strict functional isolation and eliminate UI state leakage or out-of-order rendering bugs, changeset-gating and background rendering optimizations have been completely removed.
- **Rule:** Every rendering pass for a view must be 100% functional, idempotent, and built completely from scratch using the provided `slotInfo` dataset state: the cell lists, section membership and order, and the data handed to every drawn button are recomputed each pass. What is kept between passes is only the frames themselves (a section reused for the same category, a button drawn again) and, per button, a record of the inputs it was last fully drawn with, so a button whose inputs are unchanged skips its setters (item-drawing.md §7b) — never data (layout-rendering.md §1).
- **Benefits:** Eliminating incremental delta updates guarantees that the view state remains mathematically consistent with the underlying data model, preventing the visual accumulation of ghost or out-of-sync frames.

### 7. Phase 8: Page Placement (Clean-Sweep Layout and Column-Packing)
To achieve sub-millisecond redraw performance while ensuring that the grid layout remains perfectly aligned, visually fluid, and free of overlap/gaps:
- **Rule:** Page placement is a pure, top-down clean-sweep operation. It is triggered synchronously when the data backend emits `items/RefreshBackpack/Done` or `items/RefreshBank/Done` messages.
- **Unified Views:** GridView, OneBagView, and Blizzard Bag View are handled polymorphically within `views/gridview.lua` and `views/bagview.lua`. They avoid redundant layout files by treating views as alternative naming classifications.
- **Column packing:** One pass determines the height/width of all category sections and splits them into equal-height vertical columns using the `calculateColumns` algorithm inside `frames/grid.lua`. (A second pass that shrank rows of collapsed sections went with section collapsing, which was removed.)
- **Bounds Clamping:** The view calculates the total bag height and width, clamps the parent frame within safe screen limits (`UIParent:GetHeight() * 0.90`), and toggles the scrollbars and frame points dynamically.
- **Shared, Stateless Sizing (`UpdateBagBounds`):** To ensure uniform sizing when switching tabs instantly without caching state, all bag views call a shared, stateless helper method `view:UpdateBagBounds(bag, w, h)`. This centralizes the bounds calculations, clamping, scrollbar visibility, and search-offset positioning. It is invoked at the end of the full rendering pipeline, achieving visual size parity with zero state-holding overhead.

### 8. Phase 4.5: Category Enrichment & Data Enrichment
To eliminate JIT (just-in-time) database and search engine queries during UI layout rendering, we assign final item categories and enrich item data right after search indexing and before layout/section placement occurs.
- **Rule:** Item categories must never be resolved JIT on-the-fly inside the views (`GridView` or `BagView`). Instead, they are retrieved instantly from the enriched `item.itemInfo.category` field.
- **Mechanism:** Immediately after the search index is brought up to date for this sweep (`search:SyncKind`, search-indexing.md §1 and §4) in `items:Phase8_EnrichCategories(ctx, kind, itemData, emptySlotByBagAndSlot)`:
  - Call `self:RefreshSearchCache(kind, itemData)` to update search-based category matches using the search engine.
  - Iterate over all non-empty items in `itemData` and resolve their final category by calling `items:GetCategory(ctx, item)` again. `GetCategory` is the single place where Recent Items, gear sets, custom item-list categories and search categories compete by priority (lower number wins, search wins ties). Phase 6 also calls `GetCategory`, but it does so against the *previous* sweep's search cache; the Phase 8 pass is what makes the result correct for this sweep. Never overwrite `item.itemInfo.category` with the raw search-cache entry: that bypasses the priority rules and lets a priority-10 search category beat a priority-1 custom category.
  - When the category changed, update `item.itemInfo.category` and refresh the search index's category with `search:UpdateCategoryIndex(currentItem, oldCategory)`.
  - **Live Search Results:** The active search box text is external input, in the same class as a `C_Container` read: it is consumed by the data phase and never by the draw phase. It is evaluated here (`data.isSearchResult`), never in Phase 6 and never in a view. Phase 6 runs before the index is updated, so evaluating there queries the previous sweep's index and newly looted or moved items never match until the following refresh. Views only read the pre-computed `data.isSearchResult` flag; they must not call `SearchBox:GetText()` or `search:Search()` themselves.
- **Upstream Category Visibility Filtering:** During the partition of items and categories into `slotInfo.tabs`, we query `categories:IsCategoryShown(category)`. If a category is hidden by the user, its items and its category metadata are completely omitted from `tabData.items` and `tabData.categories` upstream, so the view only ever receives and draws active, visible sections. This completely eliminates late-stage masking and filtering in the views.
- **Free Space is in the data only when there is free space:** `Phase10_PartitionIntoTabs` sets `tabData.freeSpace = { showAll, buttons }` only for a tab with at least one free-space button. A tab with no free slots (full bags, in either free-space mode, since Phase 5 records full bags with a 0 count that the aggregation drops; or no containers at all, a WoW: Forever bank before its first tab) carries no `freeSpace`, and the bag draws no Free Space section for it (layout-rendering.md §3). Before, every tab carried an empty `freeSpace`, and the draw invented one (`{ showAll = true, buttons = {} }`) for data without it, so an empty section was drawn: an empty grid reports its spacing (4) as its width, so the section's own `w == 0` check never fired and its "Free Space" header showed squeezed into two dots. Coverage: `spec/items_spec.lua` ("leaves freeSpace out of a tab with no free slots, in both free space modes").
- **Pure Data-Driven physical layout (Show Bags / `SECTION_ALL_BAGS`):** When the database layout view is set to `SECTION_ALL_BAGS`, the data phase overrides all physical item categories to their physical bag names (e.g. `#1: Backpack` or `#1: Bank`). It attaches rendering instructions to the slot data structure (`slotInfo.sectionLayouts`) indicating that these sections must be drawn headerless (`hideHeader = true`) and sorted strictly by physical slot (`sortMode = "physical"`). The view layer (`views/bagview.lua` and `views/gridview.lua`) remains completely dumb; it parses the categories and obeys `slotInfo.sectionLayouts` metadata without any hardcoded layout checks.
- **Synchronous, State-Driven Toggle:** The "Show Bags" buttons synchronously mutate the database view state and trigger an immediate recalculation (`bags/Rederive` with a fresh layout, refresh-scheduler.md §10). All asynchronous OnFinished animation hooks that previously modified state or initiated refreshes have been completely removed.
- **Obsolete Views:** Obsolete `ONE_BAG` (value 1) and `LIST` (value 3) views have been completely removed from constants and database defaults. Existing users' databases are automatically migrated to `SECTION_GRID` (Category View) via `DB:Migrate()`.

### 9. Render Passes: Clean Model, Retained Frames
To prevent ObjectPool contamination, cell leakage, and `Cannot anchor to itself` crashes while not hiding and re-showing every frame on every redraw:
- **Rule:** Every render pass starts from an empty model and releases, at its end, every frame it did not draw again. Frames are never shared between owners mid-pass: a section belongs to one view (or the bag's global sections) and is reused only for the same category; a button is released only after every renderer of the pass has run and only if no renderer claimed it.
- **Mechanism:** each view's `Render` (`GridView`, `BagView`) begins with `view:BeginRender(ctx)` (a no-op when `bagProto:Draw` already began the pass with its claim table) and ends with `view:FinishRender(ctx)`. `view:Wipe(ctx)` remains the full teardown (bag close / tab deletion) and finishes any open pass first. Layout anchors every cell to its grid's inner frame by absolute offset, so retained frames cannot form anchor cycles.
- **State Transition (`isNew` flag):** `BeginRender` (and `Wipe`) set `view.isNew = true`; `Render` sets `view.isNew = false` right after beginning.

### 10. Unidirectional, Purely Functional Pipeline and Stateless Execution
To enforce strict functional isolation and eliminate side-effects, reentrancy bugs, and half-calculated visual glitches during database updates:
- **Rule:** The entire rendering and data-refresh pipeline (`ProcessRefresh`) is structured as a purely unidirectional, functional pipeline of discrete phase functions. It avoids mutating any global or committed state (such as `self.slotInfo[kind]`) until the final phase (`Phase8_CommitAndDispatch`).
- **Transient State Isolation:** We completely avoid global/module-level JIT queries or the `_tempSlotInfo` hack.
  - An un-registered `emptySlotData` object (instantiated locally via `self:NewSlotInfo()`) acts as a transient container for empty slots, free keys, and item counts.
  - Explicit maps and dictionaries (such as `itemData` and `visibleItemsBySlotKey`) are passed linearly as arguments between the phase functions (e.g. `items:RefreshSearchCache(kind, itemData)` and `stack:AddToStack(item, itemData)`). This ensures statelessness and permanently prevents stale-state reads during calculation.
- **Commit Phase:** At the end of the pipeline, `Phase8_CommitAndDispatch` copies all calculated tables, totals, layout metadata, and the newly calculated `stackData` atomically and transactionally from the transient data structures to the real, stateful `self.slotInfo[kind]`, ensuring atomic updates and zero half-finished visual states.

### 11. Targeted Data Sweeps and Targeted State Merging
To minimize CPU frame time and `C_Container` API scanning overhead during localized item changes (such as looting an item, casting a spell, or moving an item in a single bag slot):
- **Rule:** `BAG_UPDATE` events trigger targeted bag harvesting. `Phase1_DetermineBags` intercepts `ctx:Get("targetedBags")`. When present (and not performing a forced cache `wipe`), `Phase1_DetermineBags` filters the active bag list to harvest only the specific `bagID`s that changed.
- **Nil Means All:** Global operations (sorting bags, switching tabs, category updates, initial login/UI reload, or explicit `bags/FullRefreshAll` messages) omit the `bags` field in `RefreshRequest`. When `targetedBags` is `nil` or `ctx:Get("wipe")` is `true`, `Phase1_DetermineBags` automatically falls back to sweeping all available container bags.
- **Targeted Merging:** In `ProcessRefresh`, when a targeted sweep completes, newly harvested `itemData` for the targeted bags is merged with `previousItems`: slot keys belonging to targeted bags are cleared from `previousItems`, and newly harvested slots are inserted. The resulting complete, unified `itemData` dictionary is then passed down to downstream phases (virtual stacking, search indexing, category enrichment, sorting, tab partitioning), ensuring downstream phases always operate on a 100% complete model of all bags. `previousItems` is read *after* the frame boundary (§3); because the refresh queue is serialized (refresh-scheduler.md), it always reflects the fully-committed state of the strictly-previous unit — a wipe unit queued alongside a targeted unit commits its full sweep before the targeted unit runs, so the targeted merge preserves every untouched bag.
- **Moved Items (`Phase4_ClearMovedItemGlows`):** An item whose GUID disappears from one slot and appears in another in the same sweep was moved, not looted. Its new-item state is cleared through `items:ClearNewItemFromData(ctx, addedItem)` on the harvested data object. Phase functions must never reach for committed state (`GetItemDataFromSlotKey`) to mutate an item they were handed: the committed entry for the destination slot is the previous occupant of that slot (or nothing), so the moved item's GUID timer would never be cleared and it would stay in Recent Items.
- **Classic Base Bank Support:** On Classic/Era clients, `PLAYERBANKSLOTS_CHANGED` passes `bags = { [-1] = true }` to target the base bank slot changes specifically, preventing unnecessary full bank cache wipes.
- **Per-slot reuse within harvested bags:** a targeted bag is still harvested slot by slot, but a slot whose contents are unchanged keeps its committed item (§16), so a one-potion sweep reads one slot of the bag, not all of them.

### 12. Scoped Recent Item Tracking and Sort Pipeline Integration
To prevent global side-effects where sorting or clearing recent items in one container (e.g. Backpack) accidentally clears recent item timers in another container (e.g. Bank/Warbank):
- **Scoped Timers:** `_newItemTimers` inside `data/items.lua` is strictly scoped by `BAG_KIND` (`BACKPACK` vs `BANK`).
- **Targeted Clearing:** `items:ClearNewItems(kind)` accepts a `BAG_KIND`. Passing `BACKPACK` clears only `BACKPACK` timers and invocations of `C_NewItems.RemoveNewItem` for backpack bag IDs. Passing `BANK` clears only `BANK` timers and `C_NewItems` for bank and account bank bag IDs.
- **Sort Integration:** Sorting requests (`request.sort`, `request.sortBank`, `request.sortWarbank` in `data/refresh.lua`) trigger targeted `items:ClearNewItems(kind)` and mark the kind's sort sweep pending (`items:MarkSortSweepPending`). When the client can sort, the Blizzard sorting API (`C_Container.SortBags`, `SortBankBags`, or `SortAccountBankBags`) is called straight away and the sort's own unit does not sweep: the next committed sweep of that kind (normally the moves' `BAG_UPDATE` refresh, else the 0.5 s fallback) re-reads every bag of the kind with a fresh layout, which clears Recent Items and re-enriches categories in one redraw. In combat, or without a sort API, the kind is swept at once. Full contract: refresh-scheduler.md §6.
- **"All Items Recent" (client-flag-independent acquisition detection):** Recent Items membership is the `_newItemTimers` GUID timer alone; the client's `C_NewItems` flag only starts that timer and drives the glow, and timers end only when the bag closes (recent-items.md). But WoW does **not** set the `C_NewItems` flag for items auto-looted from an opened container (a loot bag, lockbox, etc.). To make those show up under Recent Items, the `database:GetMarkRecentItems(kind)` option ("All Items Recent") drives `items:MarkAddedItemsRecent(ctx, kind, previousItems, itemData)`, called in `ProcessRefresh` immediately after `Phase4_ClearMovedItemGlows` (so timers seed before `Phase8_EnrichCategories` re-resolves categories via `GetCategory` → `IsNewItem`).
  - **Acquisition = new GUID.** An item is "acquired" (and marked recent via `items:MarkItemAsNew`, which seeds `_newItemTimers[kind][guid]`) when its `itemGUID` is absent from every entry in the previously committed `previousItems`. This covers a brand-new slot, a slot filled in place (the container's own freed slot receiving one of its contents — a hash change), and — because opening a container removes it and adds its contents in the **same** targeted sweep — the exact same-frame remove+add the container case produces.
  - **A grown stack counts.** A slot whose GUID was already there is acquired when its count grew and its item ID's total count in the kind grew too. The client did not flag the stack a captured vendor purchase grew (`C_NewItems.IsNewItem` false for its slot), so without this a purchase onto a stack never reached Recent Items. A stack merged into by hand grows while another shrinks or disappears, so the total is unchanged and it does not count. Coverage: `spec/refresh_pipeline_spec.lua` ("All Items Recent: a stack that grows": a replay of the captured purchase, hand merges, the option off, a running timer kept).
  - **Moves are excluded.** A pure move re-uses the same `itemGUID` in a different slot; that GUID is present in `previousItems`, so `MarkAddedItemsRecent` skips it, and `Phase4_ClearMovedItemGlows` still clears any stale recency for it. This keeps drags/moves out of Recent Items.
  - **Gating.** Runs only on `addon.isRetail`, only for `BAG_KIND.BACKPACK` (bank items are viewed, not acquired), only when the option is on, and never on a `wipe` refresh (initial login / UI reload / full cache wipe must not flood Recent Items — `_firstLoad` forces `wipe` on the first sweep per kind). Coverage: `spec/refresh_pipeline_spec.lua` ("All Items Recent (container auto-loot, same-frame remove + add)").

### 13. Persistent Empty Gaps (Diff-Driven, No Held State)
To reproduce the classic "the bag doesn't collapse while it's open" behavior, when a displayed item icon leaves a slot (consumed, sold, destroyed, or moved out — including the last physical stack of a virtual stack) we leave a **true empty gap** at that item's exact position in its category section. The gap is a real hole in the grid (no item frame at all), it persists across refreshes, it persists even when new items are added elsewhere, and it collapses only on **Sort**, **bag close**, **bank open**, or a full **wipe**.
- **It is a data-structure problem, not a rendering problem.** The renderer already accepts `isItemGap` nodes (views turn them into frameless `{ isGap = true, width = 37, height = 37 }` cells that `frames/grid.lua` lays out as reserved holes). No view or grid math changed. The only render-side fix was making `sectionProto:ReleaseAllCells` (`frames/section.lua`) skip gap cells, which have no `Release` method.
- **The global `Recent Items` header section is not a tab view and must also consume the ordered `sortedItems`.** `Recent Items` (and `Free Space`) are excluded from the tab views by `ItemBelongsToTab`, so the diff-driven order and gaps never reach them through `tabData.items`; they are drawn by `bagProto:DrawGlobalSections` (`frames/bag.lua`). That method iterates `slotInfo.sortedItems` (this sweep's committed ordered layout) to build the Recent Items section — keeping entries whose category is `Recent Items`, preserving both the stable item order and the persistent `isItemGap` holes — instead of scanning the unordered visible-item map. Scanning `slotInfo:GetVisibleItems()` via `pairs()` (the old behavior) rendered Recent Items in an arbitrary, per-sweep-shuffling order and dropped every gap, because gaps exist only in `sortedItems` and never in the visible map (so consuming an item collapsed its slot even with "Preserve Empty Slots as Gaps" on). See layout-rendering.md § 1 and `spec/frames/bag_draw_ownership_spec.lua`.
- **No bespoke held state.** The pipeline stays a stateless clean-sweep (§6, §10). The "previous view" is simply the already-committed `self.slotInfo[kind].sortedItems` (now surfaced by `Phase3_ExtractPreviousState` as a third return, `previousSortedItems`); the "new view" is this sweep's `visibleItemsBySlotKey`. Gaps ride forward inside the committed `sortedItems`, so they persist with zero extra structures to hold or clear.
- **The diff (`items:BuildOrderedItems`, replaces the direct `Phase9_Sort` call in `ProcessRefresh`):** matches previous layout entries against current displayed items **bucketed by `itemHash`** (not GUID — a virtual-stack re-root changes the root's GUID but not its hash). Per hash: (1) a previous slotkey still displayed **survives in place**; (2) leftover current items of that hash fill leftover previous slots of that hash (a move or re-root **rekeys in place, no gap**). Then, across hashes: (3) a previous entry the hash passes left unmatched **keeps its position** when its own slot now displays an item with the **same, non-empty item GUID** that the hash passes also left unused (the item's hash changed without it leaving; see the next bullet); (4) any previous entry still with no current match becomes a **gap** (a `CloneAsGap` of the departed entry — a shallow copy carrying `bagid`/`itemInfo.category`/`itemHash` so `ItemBelongsToTab` routes the hole to the same tab, `isItemGap = true`, and slotkey `"gap:"..originalSlotkey` which never collides with a real `"bagid_slotid"`); (5) genuinely new displayed items are **appended** at the end of their category in fresh attribute-sort order (they never backfill a gap). Gaps are excluded from `totalItems` (Phase 10) and keep their category alive in the category tally.
- **An item whose hash changed in its own slot is not a departure (step 3).** `itemHash` is a content key (§16, virtual-stacks.md §4), and several of its inputs read differently before and after the client has an item's data: the current item level falls back to 0 or the base level, the bind type falls back to 0 (changing the binding scope), and `GetItemStats` returns nothing. An enchant, a gem, an item level upgrade or a scaling item's level-up also rehash an item that never moved. Before step 3, any such sweep while the bag was open turned the item into a gap and re-appended it at the end of its section.
  - **Failure mode (login, fixed):** a cold read at login also files items under "<Type> - Classic" (`expacID` falls back to 0). With the bag open while the cache warmed, every "– Classic" section filled with holes (or became header-only), and every other section showed N holes followed by the same N items. v0.5.14 re-read every slot on every sweep, so any hash input resolving late rehashed every item.
  - **The slot must match**, not just the GUID: a move between the Character Bank and the Warbank changes the hash on purpose (the `"W"` scope, virtual-stacks.md §6) and must stay a remove + add, because the item changes tab set. Matching on GUID alone turned that move into an in-place keep and collapsed the Character Bank tab's hole.
  - **It runs after the hash passes**, so every case the hash passes resolve behaves exactly as before. The cost: an item whose new hash equals that of an identical item that left in the same sweep takes the departed item's entry (pass 2), and its own entry becomes the gap.
  - **Empty GUIDs never pair**, so a client read with no GUID falls back to the old remove + add.
  - **Virtual stacks:** stacking itself is untouched (Phase 7 keys on the hash before the diff runs). A stack whose piles all rehash with the same root keeps its position, since its visible root keeps its slot and GUID. Still a gap: a pile whose new hash joins a different, already-placed stack (its visible entry is gone into the stack), and a stack that rehashes and re-roots to another pile in the same sweep.
  - Coverage: `spec/gap_reconciliation_spec.lua` ("an item whose hash changed in its own slot") and `spec/refresh_pipeline_spec.lua` ("items whose hash changes without leaving their slot": the login warm-up, a virtual stack whose piles all rehash, the Character Bank to Warbank move).
- **Reset (fresh, gapless attribute sort) vs. diff:** `BuildOrderedItems` returns a plain `Phase9_Sort` (no gaps) when the physical bag view (`SECTION_ALL_BAGS`, which already renders empties in place and never collapses), when the option is off, when `ctx:Get("resetLayout")` is set, when the bag is closed (`items:IsBagOpen(kind)` is false), or when there is no previous layout (first load / post-wipe). That gapless result becomes the next baseline.
- **Lifecycle triggers.** `resetLayout` is set by the first sweep after a Sort (`items:RunRefresh` when the kind's sort sweep is pending, refresh-scheduler.md §6) and on `BANKFRAME_OPENED` (opening the bank starts clean). Full wipes (`bags/FullRefreshAll`, `BAG_CONTAINER_UPDATE`, etc.) reset the slotInfo, so `previousSortedItems` is empty and the sweep is gapless; settings, category and interaction recalculations set `resetLayout`. Bag close reuses the dormant `drawOnClose` flag: `BuildOrderedItems` calls `items:MarkDrawOnClose(kind)` whenever it emits a gap or keeps a rehashed item at its old position (step 3; that position can be out of sort order, e.g. a login item whose category and name were read cold), and `bagProto:OnClosed` (`frames/bag.lua`, run from the bag frame's own `OnHide`, so every close path including ESC) refreshes once when `drawOnClose` is set or Recent Items expired (recent-items.md §3) — the frame is hidden by then, so the on-close sweep sees `IsBagOpen == false` and commits a collapsed layout. Consuming items while the bag is closed likewise never accrues gaps.
- **Per-kind scoping.** State lives entirely in each kind's committed `slotInfo[kind].sortedItems`, so backpack and bank/warbank gaps are structurally isolated; a bank consume can never gap the backpack.
- **Option.** `database:GetPreserveItemGaps(kind)` / `SetPreserveItemGaps(kind, value)` (default **on** per kind via `const.DATABASE_DEFAULTS`), exposed as the "Preserve Empty Slots as Gaps" checkbox in `config/config.lua`; toggling it sends `bags/FullRefreshAll` for a clean transition.

### 14. Equipment-Set (Gear Set) Location Map Is Rebuilt Every Sweep
BetterBags labels WoW equipment-set (`C_EquipmentSet`) members with a `Gear: <SetName>` category. `data/equipmentsets.lua` maintains `bagAndSlotToSet[bag][slot] = {setName, ...}`, a map keyed by **physical (bag, slot)** built from `C_EquipmentSet.GetItemLocations`, and the harvest reads it per slot via `equipmentSets:GetItemSets(bagid, slotid)` (`data/items.lua`, into `data.itemInfo.equipmentSets`); `GetCategory` turns a non-nil `equipmentSets` into `"Gear: " .. equipmentSets[1]` at top priority (after Recent Items).
- **Rule:** `items:RunRefresh` calls `equipmentSets:Update()` as its **first** step, before `Phase1_DetermineBags`/`Phase2_Harvest`, so the location map is rebuilt in the same frame the harvest reads it. Because the map is keyed by physical slot (not by item GUID), a stale map mislabels whatever item currently occupies a slot a set item used to occupy.
- **Failure mode (regression from #1037):** the legacy pipeline called `equipmentSets:Update()` at the top of `RefreshBags`; the refactor that promoted the phase pipeline to canonical names dropped it, leaving `equipmentSets:OnEnable` (login/`/reload` only) as the sole caller. The map then froze at login state: a newly looted item dropped into a slot a set piece had vacated inherited that piece's `Gear: <Set>` label, set pieces that moved lost their label ("gear sets disappeared"), and a set that resolved to a new name after a spec switch kept the old label. `EQUIPMENT_SETS_CHANGED` (`data/refresh.lua`) already requested a refresh, but that only re-harvested against the (still stale) map — the map itself is only refreshed by the per-sweep `Update()`.
- **Cost / scope.** `Update()` is cheap (a few `C_EquipmentSet` calls per set) and internally no-ops on Classic/Anniversary. Rebuilding the full map every sweep is correct even for targeted sweeps: only harvested slots re-read `GetItemSets`, and set-membership changes fire `EQUIPMENT_SETS_CHANGED` → a recalculation of both bags, which refreshes every kept item's sets (`items:RefreshKeptItem`).
- **Coverage:** `spec/refresh_pipeline_spec.lua` ("gear set labeling (C_EquipmentSet)") and the map-building unit tests in `spec/equipmentsets_spec.lua`. Any spec that stubs `EquipmentSets` and drives the pipeline must give the stub a no-op `Update` (the sweep now calls it).


### 15. Upgrade Icon Provider Resolution (External-Provider Precedence + Robust Registration)
Upgrade arrows (`data.isUpgrade`, resolved in `Phase6_EnrichData` via `items:ResolveUpgrade`, drawn by `itemProto:UpdateUpgrade` in `frames/item.lua`) are produced by a registered provider. `items:Init` registers the built-in `"BetterBags"` provider — a per-inventory-slot item-level comparison (higher `currentItemLevel` than the item equipped in that slot, or an empty slot ⇒ upgrade) **gated by usability, level, spec and handedness** so it does not arrow gear the character can't or shouldn't wear:
  - **Usability gate (`C_PlayerInfo.CanUseItem(itemID)`):** items the character cannot use at all (class/weapon proficiency — e.g. a staff for a warrior) never arrow. Guarded by API existence, so clients without it keep the pure ilvl comparison.
  - **Preferred-armor gate (`items:IsNonPreferredArmorType` → `IsItemPreferredArmorType(itemLocation)`):** wearable armor of one of the four types (Cloth=1/Leather=2/Mail=3/Plate=4) that is not the character's preferred armor type (e.g. cloth on a plate wearer) never arrows, mirroring Blizzard's own "not your best armor type" bind warning. Shields (subclass 6), cloaks (armor subclass Cloth but `INVTYPE_CLOAK`, universally wearable), cosmetic/generic armor, and all non-armor items are never gated. Both APIs are retail-verified (`CanUseItem` 10.0.5+, `IsItemPreferredArmorType` 11.0+); there is **no** native "is-upgrade" API on retail (`IsContainerItemAnUpgrade` was removed in 10.0.2).
  - **Level gate:** an item whose `itemMinLevel` is above `UnitLevel("player")` never arrows.
  - **Primary-stat gate:** the spec's primary stat is read the way Blizzard's paper doll does (`C_SpecializationInfo.GetSpecialization`, then the 6th return of `GetSpecializationInfo`, an `LE_UNIT_STAT_*` value). An item that carries primary stats, none of them the spec's, never arrows (an Intellect cloak for a Strength spec). Primary stats are read from the `GetItemStats` keys (`C_Item.GetItemStats`, or the global on Classic): `ITEM_MOD_STRENGTH_SHORT` / `_AGILITY_` / `_INTELLECT_`, and the combined `ITEM_MOD_X_OR_Y_SHORT` keys the global strings define. A real retail multi-primary shield reports each primary as its own key. Items with no primary stat (rings, necks, many trinkets, old weapons) are not gated, nor is anything when the client reports no primary stat (no spec, `0`, or a client without it).
  - **Handedness (Pawn's rule):** while a two-hander or ranged weapon is in the main hand, one-handers, off-hand weapons, shields and held items never arrow; while a one-hander is in the main hand, melee two-handers never arrow. Ranged weapons are not ruled out by a one-hander: on Classic they go in their own slot (`INVSLOT_RANGED`). A one-hander (`INVTYPE_WEAPON`) is compared with the off-hand slot only when `CanDualWield()`.
  - **Empty slots:** an empty equipped slot is an upgrade for anything that fits it, except a copy of a ring or trinket already worn in its other slot (they are nearly always unique-equipped). Shirts and tabards are never upgrades. `equipmentCache` is nil until the first backpack sweep reads the gear; until then the provider arrows nothing (every slot would look empty) and no verdict is kept.
  Secondary-stat weighting is the one thing left to Pawn.

  The smart providers are the external integrations `"Pawn"` (`integrations/pawn.lua`) and `"SimpleItemLevel"` (`integrations/simpleitemlevel.lua`), which register themselves via `items:RegisterUpgradeProvider` in their `OnEnable`.
- **Precedence rule (`items:GetActiveUpgradeProvider`, the single resolver used by both `ResolveUpgrade` and the config dropdown's `getValue`):** if the user has **explicitly** chosen a provider (`database:GetUpgradeIconProviderUserSet()` is true — the flag is set only by `DB:SetUpgradeIconProvider`, i.e. the config dropdown `setValue`), honor `database:GetUpgradeIconProvider()` exactly. Otherwise (legacy default, setting never touched) an available external provider **takes precedence** over the stored `"None"`/`"BetterBags"` value, `"Pawn"` winning over `"SimpleItemLevel"`. `upgradeIconProviderUserSet` defaults to `false` (`const.DATABASE_DEFAULTS`) so existing users automatically get Pawn/SimpleItemLevel arrows again.
- **Failure mode (regression from #1036):** pre-#1036 the Pawn integration registered an always-on `bag/Rendered` handler that **overrode** every arrow with Pawn's verdict, so Pawn users got correct arrows regardless of the (never-Pawn) dropdown value. #1036 turned Pawn into an opt-in provider consulted only when `upgradeIconProvider == "Pawn"`, with no migration — so existing users silently fell back to the naive `"BetterBags"` provider (arrows on wrong armor types / wrong stats), and `"Pawn"` was a value they had never selected. `GetActiveUpgradeProvider`'s precedence restores the automatic behavior without overriding a real explicit choice.
- **Verdict cache (built-in provider only):** the built-in provider's verdicts are kept on each item and reused until an input changes; the inputs and their invalidations are in caches.md §2. Pawn and SimpleItemLevel are asked on every sweep; why Pawn is not cached is in caches.md §2.
- **Robust registration (load-order resilience):** `pawn:OnEnable`/`simpleItemLevel:OnEnable` delegate to a `:Register()` helper that early-returns `false` when the external addon's globals are absent. When that happens `OnEnable` registers an `ADDON_LOADED` retry (via the `Events` module) so the provider still appears once the external addon finishes loading — otherwise a load-order race left the provider (and its dropdown entry) permanently missing. `:Register()` is idempotent (guarded by `self._registered`) and prints the "integration enabled" line exactly once.
- **Config dropdown:** the items list is built dynamically from `items.upgradeProviders` (`config/config.lua`), and `getValue` highlights `items:GetActiveUpgradeProvider()` (the provider actually in effect), so the highlighted option matches the arrows being drawn even when precedence is active.
- **Coverage:** `spec/items_spec.lua` ("Upgrade Icon Providers": built-in usability gating — CanUseItem, preferred-armor, cloak/shield/weapon exclusions, and the graceful naive fallback when the APIs are absent — empty slots, handedness and dual wield, the level gate, and the primary-stat gate including real retail items' stat keys — plus Pawn/SimpleItemLevel registration, late ADDON_LOADED registration, precedence, and explicit-choice override) and `spec/database_spec.lua` ("tracks whether the user explicitly set a provider").

### 16. Per-Slot Harvest Cache (Unchanged Slots Keep Their Item)
`AttachItemInfo` costs on the order of 100 µs per slot in the client (about fifteen client API calls plus link parsing and the stat hash), and a targeted sweep harvests every slot of every bag `BAG_UPDATE` named. Using a potion re-read all 20-36 slots of its bag for one count change (~2.7 ms of a profiled refresh on WoW: Forever).
- **Rule:** `items:Harvest` (Phase 2) receives the kind's committed `itemsBySlotKey` on every sweep that is not a wipe, and for each slot calls `items:ReuseHarvestedSlot`. A slot keeps its committed ItemData when the client's `ContainerItemInfo` matches what the item was read from (item ID, hyperlink, count, name, icon, quality, lock, bound, readable, loot, filtered, no-value), its item GUID matches (two identical full stacks swapped between slots match on every container field but not on GUID), **and** its `C_Item.GetCurrentItemLevel` matches (scaling changes an item's current item level without changing its link). The full invalidation list for every cache is in caches.md. Otherwise the slot goes through `AttachItemInfo`, which is handed the container info the check already read.
- **Refreshed on a kept item** (`items:RefreshKeptItem`, which recalculations, refresh-scheduler.md §10, also run on every item still in its slot)**:** the fields that change without the slot's contents changing, each computed exactly as `AttachItemInfo` computes it: `itemInfo.isNewItem` (`items:ClientNewItemFlag`: the client's `C_NewItems` flag alone, which drives the glow; the Recent Items timer, seeded by the shared `items:SeedNewItemTimer`, decides the category through `IsNewItem` in `GetCategory`), `itemInfo.equipmentSets` (the set map is rebuilt every sweep, §14), `questInfo`, and `itemInfo.tooltipText` (a cache hit in the tooltip scanner, or a re-scan after a `TOOLTIP_DATA_UPDATE` invalidated it, tooltip-scanning.md). A kept item must match what a fresh read of the slot would produce; `spec/refresh_pipeline_spec.lua` compares the new-item flag of a kept slot with an `AttachItemInfo` read of the same slot after the player hovered it.
- **Nothing else is written to a kept item during the harvest.** It is still the committed item until the sweep commits a frame later (the harvest runs before the sweep's yield), and the bag can draw from committed state in between (a tab switch, a bag opening with a pending draw). Every derived field (category, virtual stack root and total, search match, upgrade, context match, draw generation) is rewritten by Phases 6-8 every sweep, after the yield, exactly as for items in bags the sweep did not visit, which have always been carried over as the same objects. Writing a derived field early showed a stack root's own pile count instead of its total for that frame.
- **Never reused:** empty slots (cheap to read), a slot read while the client had no item info for it (`harvestIncomplete`: `GetItemInfo` returned nil or there was no container info, the issue #1090 cold cache), and any sweep with `wipe` (all of `bags/FullRefreshAll`, `BAG_CONTAINER_UPDATE`, `EQUIPMENT_SETS_CHANGED` and the first sweep, which also run against an emptied committed state).
- **Raw values:** `AttachItemInfo` fills fallbacks into `containerInfo` (`itemName`, `iconFileID`, `quality`), so it saves the values the client returned as `rawItemName`/`rawIconFileID`/`rawQuality` and the check compares against those; comparing against the filled values would make a slot with a client-side nil never match.
- **Virtual stacks:** stacking keys on `itemHash`, which a kept item keeps (it is computed from the link, binding and stats, all unchanged by definition). `Phase7_ApplyVirtualStacks` re-totals every stack from the current `currentItemCount` of every pile each sweep, so a kept pile counts correctly, re-roots when another pile overtakes it, and unmerges when a stacking rule stops applying.
- **Known staleness (same as an unvisited bag):** state the client changes without changing the slot and without a container event, such as a refundable purchase's binding expiring or an appearance being collected, is not re-read until the slot changes or a wipe sweep runs.
- **The maximum item level** (for item level colors) is learned in `AttachItemInfo`, which kept slots skip, so `DB:ResetMaxItemLevel` sends `bags/FullRefreshAll` to re-read every slot.
- **Coverage:** `spec/refresh_pipeline_spec.lua` ("per-slot harvest cache": kept vs. re-read slots, one re-read per compared container field, a single container-info read for a changed slot, GUID change, wipe, cold item info, the new-item flag matching a fresh read, committed items untouched until the commit, refreshed volatile fields, and virtual stacks re-totalled, re-rooted and unmerged over kept piles) and `spec/database_spec.lua` ("ResetMaxItemLevel requests a full refresh").

### 17. Draw Generation
Every item carries `drawGeneration`, stamped in `Phase6_EnrichData` from `items._drawGeneration[kind]`, which `RunRefresh` bumps on every wipe sweep of the kind. Item buttons include it in the inputs that decide whether a redraw can be skipped (item-drawing.md §7b): a setting the data phase reads (stacking rules, the upgrade provider) sends `bags/FullRefreshAll`, a wipe, so a new generation makes every button of the kind draw in full. It is per kind, so a bank wipe does not redraw the backpack. Settings that only change how a button draws (glow intensity, item level display) do not wipe: they redraw with `ItemFrame:RestyleButtons()`, and a theme change bumps `themes.decorationGeneration` (refresh-scheduler.md §9). Coverage: `spec/refresh_pipeline_spec.lua` ("draw generation").
